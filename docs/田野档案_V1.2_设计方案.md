# 田野档案 V1.2：公众门户、角色权限与农户准入设计

> 项目：《基于SpringBoot的农产品产地溯源信息管理系统设计与实现》  
> 技术基线：Spring Boot 3.5.16 / JDK 17 / MyBatis-Plus 3.5.17 / MySQL 8.0.36 / Vue 2.7.16 / Element UI。  
> 本文件为实施设计，不表示功能已经部署或测试通过。

## 1. 设计决策

- 保留现有「田野档案」配色、字体和视觉风格；不再用“开发计划、系统运行状态”充当面向消费者的首页内容。
- 站点默认进入公开的公众门户，所有人均可查询**已发布**的溯源批次、公开产品、公开公告和真实聚合统计。
- 后台仅有两个可登录角色：`ADMIN`（管理员）、`FARMER`（通过资质审核的农户）。`GUEST` 是未登录访问态，不写入 `sys_user.role_code`。
- 注册审查（账号是否允许录入）和批次审核（录入数据是否允许公开）是两道独立关口。审核仅降低滥用风险，**不等于对农产品真实性/质量作出保证**。
- V1 暂不实现农户经营主体多员工、多基地协同管理。一个农户账号可关联多个基地和农产品。
- 身份材料不能通过静态文件 URL 公开；收集范围遵循必要性原则，尽量不用完整身份证照片。

## 2. 访客与后台三种布局

### 2.1 公众门户（GUEST，不登录）

布局：顶部品牌与导航 + 数据门户首页 + 查询页面；移动端顶部折叠菜单，不出现管理员后台侧边栏。

顶部导航：`首页` / `溯源查询` / `产地与产品` / `平台公告` / `农户入驻` / `登录`。

### 2.2 农户工作台（FARMER，审核通过后登录）

左侧菜单：`我的工作台` / `种植基地` / `农产品档案` / `溯源批次` / `农事记录` / `采收记录` / `质量检测` / `流通记录` / `信息完整性` / `我的申请与资料`；页头提供 `返回公众首页` 和 `退出登录`。

农户：只能操作归属自己的业务数据；批次从 `DRAFT` 提交到 `SUBMITTED`，没有直接设置 `PUBLISHED` 的权力。

### 2.3 管理后台（ADMIN）

左侧菜单：`管理概览` / `农户资质审核` / `账号管理` / `种植基地监管` / `农产品管理` / `批次审核` / `农事与流通监督` / `完整性规则` / `平台公告管理` / `数据统计`。管理员操作应有审计记录。

## 3. 公众首页改版

### 首屏

保留绿底原创主视觉，但首要操作改为“输入溯源码 / 扫码查询”，右侧显示最近公告。首页不要把后端状态、环境、开发进度、Git 版本等信息暴露为主要内容。

### 数据指标（从后端读取，严禁编造）

1. 已公开溯源批次数：`trace_batch.status='PUBLISHED'` 的数量。
2. 公开产品数：上述批次中 `DISTINCT product_id`。
3. 参与基地数：上述批次中 `DISTINCT base_id`。
4. 覆盖地区数：已公开批次关联的种植基地省市组合数（按真实所在地统计）。

重要：**目前库里仅有一条模拟基地数据，未必存在已发布批次。显示 0 和“暂无公开数据”是正确行为。** 测试基地不能被误表述为真实可追溯来源。将来导入正式数据要区分演示数据。

### ECharts 图表

- 近 6 个月已公开批次变化：按 `trace_batch.published_at` 月份聚合，折线图/柱状图。
- 公开农产品分类：按 `trace_batch -> agri_product -> product_category` 关联统计，横向柱状图；可选用占比饼图，但类别少时无需强行展示饼图。
- 已公开批次地区分布：省份 TOP 6 柱状图，避免额外引入地理底图和复杂地图 API。
- 全部可视化应有空数据状态、加载状态、错误提示、统计口径说明，不使用前端写死的业务数值。

前端建议直接安装 `echarts@5.6.0`，由 Vue 2 组件在 `mounted()` 中初始化，并在窗口变化时 resize、`beforeDestroy()` 中 dispose；不需要额外引入 Vue 3 的封装库。

### 平台公告

首页右侧显示最新 3~5 条公开公告，含标题、类型、发布时间；置顶项优先。点击进入公告详情。

`sys_notice` 只有 `PUBLISHED` 且在可见时间窗口中的内容可公开；管理员可编辑、发布、撤回、置顶。避免用 `v-html` 直接渲染未经清理的富文本。

## 4. 农户注册和审核流程

```text
游客点击“农户入驻”
    ↓
填写用户名/密码、联系资料、经营地点、资质说明及证明材料
    ↓
注册服务创建 sys_user：role_code=FARMER，status=0
并创建 farmer_application：review_status=PENDING
    ↓
管理员登录，在“农户资质审核”查看申请与私有材料
    ├─ 驳回：申请标记 REJECTED，账号仍不可登录；保留原因供重新提交
    └─ 通过：在事务中将申请改为 APPROVED，账号 status=1
    ↓
农户登录 → 进入本人工作台 → 创建基地和产品 → 提交溯源批次
    ↓
管理员独立审核批次 → 批次 PUBLISHED → 公众才可查询
```

### 身份证明材料设计原则

- 优先提供经营/种植相关证明，例如合作社营业执照（可遮盖无关信息）、土地经营或流转相关凭证、村级证明等，按申请主体类型提示可接受材料，不强制所有农户提交同一类个人证件。
- 仅限审核人员访问，不存放到 `frontend/public` 或直接公开的静态资源目录。
- 限制文件大小、类型、数量，校验文件真实格式并随机重命名；下载时校验 ADMIN 身份。
- 前端提供告知、同意及材料使用目的说明；正式部署还需约定保存期限、过期清理、数据访问与删除机制。
- 账号状态沿用现有 `sys_user.status`：`0=禁用/未启用`，`1=启用`；申请状态由 `farmer_application.review_status` 表达。当前 `sys_user.status` 默认值是1，**注册 Service 必须显式写入0，不能依赖默认值**。
- 公开注册请求不可接受 `role_code`、`status`、`reviewer_id` 等权限字段；这些只能由服务端决定。

## 5. 数据库变更

当前 V1 有14张表；V1.2只需新增：

- `farmer_application`：农户资质申请、文件私有路径、审核状态、审核人、意见、时间；允许保留历史申请。
- `sys_notice`：公告标题、正文、草稿/发布/撤回、置顶、发布时间、过期时间、创建与更新人。

其余沿用：`sys_user` 的 `ADMIN/FARMER`、`planting_base.owner_id`、`agri_product.owner_id`、`trace_batch.owner_id/status`、`batch_audit`。已有 `trace_batch.status`：`DRAFT/SUBMITTED/PUBLISHED/REJECTED`。

对应的增量建表脚本：`sql/05_portal_auth_notice.sql`。运行前备份数据；脚本仅 CREATE，不 DROP 或 TRUNCATE。

## 6. 接口规划

| HTTP | 路径 | 谁可访问 | 内容 |
|---|---|---|---|
| GET | `/api/public/stats/overview` | 游客 | 4项公开统计指标 |
| GET | `/api/public/stats/trend` | 游客 | 近6个月公开批次趋势 |
| GET | `/api/public/stats/categories` | 游客 | 分类统计 |
| GET | `/api/public/stats/regions` | 游客 | 地区分布 |
| GET | `/api/public/notices` | 游客 | 公开公告列表 |
| GET | `/api/public/notices/{id}` | 游客 | 公开公告详情 |
| GET | `/api/public/trace/{code}` | 游客 | 仅已发布批次公开信息 |
| POST | `/api/auth/farmer/register` | 游客 | 提交农户注册申请 |
| POST | `/api/auth/login` | 管理员/通过审核农户 | 登录 |
| GET | `/api/auth/me` | 已登录 | 当前角色与身份 |
| GET | `/api/admin/farmer-applications` | 管理员 | 待审/已审申请分页 |
| POST | `/api/admin/farmer-applications/{id}/approve` | 管理员 | 批准申请与启用账号（事务） |
| POST | `/api/admin/farmer-applications/{id}/reject` | 管理员 | 驳回并记载意见 |
| POST/PUT | `/api/admin/notices` | 管理员 | 新建/修改公告 |
| POST | `/api/admin/notices/{id}/publish` | 管理员 | 发布公告 |
| POST | `/api/admin/notices/{id}/withdraw` | 管理员 | 撤回公告 |
| GET | `/api/farmer/dashboard` | 农户 | 仅个人数据统计 |
| ... | `/api/farmer/bases` 等 | 农户 | 仅个人名下业务资源 |

建议公共响应仍用 `ApiResponse<T>`。参数错误400、未认证401、已认证但越权403，服务器出错500；不要将数据库原始异常返回前端。

## 7. 前端路由与菜单架构

当前项目已有 `AppShell.vue`、`Dashboard.vue`、`router/index.js`，均按单一管理后台设计。V1.2应进行结构性拆分，避免在一个侧边栏里堆满三类角色判断。

```text
src/
  layouts/
    PublicLayout.vue
    AdminLayout.vue
    FarmerLayout.vue
  views/
    public/Home.vue
    public/Search.vue
    public/TraceDetail.vue
    public/Notices.vue
    public/FarmerApply.vue
    auth/Login.vue
    admin/Dashboard.vue
    admin/FarmerReview.vue
    admin/NoticeManage.vue
    farmer/Dashboard.vue
    farmer/MyBases.vue
  router/index.js
  store/auth.js                # 也可用 Vuex 3.x
  api/public.js
  api/auth.js
  api/admin.js
```

路由约定：`/`、`/search`、`/trace/:code`、`/notices`、`/farmer-apply` 无需登录；`/admin/*` 仅 ADMIN；`/farmer/*` 仅审核通过的 FARMER。登录后按服务器返回的角色跳转。前端菜单与路由守卫只负责体验，后端仍需逐请求校验权限、资源归属。

## 8. 建议开发顺序与验收

1. 提交当前 V1.1 前端稳定代码，创建 `feature/portal-roles` 分支。
2. 备份数据库，执行 `05_portal_auth_notice.sql`，让生成器仅为两张新表生成基础骨架（不能直接开放自动生成的写接口）。
3. 先拆布局：把当前首页从管理后台独立为公开首页；管理员、农户后台分别拥有左侧菜单。
4. 建公告 CRUD 和公开只读接口，先用管理员测试账号录入一条测试公告。
5. 开发公开聚合统计接口与 ECharts 图表，确保零数据时正常显示。
6. 开发注册、私有证据上传、管理员审核、登录、权限校验。
7. 农户个人数据权限、批次独立审核与发布流程测试。

### 核心测试（必须通过）

- 未登录可查询已发布批次和公告；不能查询草稿，也不能访问管理接口。
- 待审核农户不能登录后台；被拒绝后不能通过修改请求参数启用账号。
- 普通农户不能越权修改另一农户的基地、产品与批次。
- 农户不能将自己的批次直接改成 PUBLISHED。
- 管理员发布公告后游客可见，撤回后游客不可见。
- 无公开批次时图表显示“暂无公开数据”，不能使用模拟数据冒充平台统计。
- 上传的证明文件不能通过猜测 URL 被游客下载。

## 9. 当前阶段的边界

这份文件是下一阶段的设计基线。**不表示已经实现新的页面、统计接口、审核或权限功能。** 先完成数据模型和路由边界，再实施登录功能，可以减少后续重构。
