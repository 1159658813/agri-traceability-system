# 农产品产地溯源系统：V1 数据库整体设计与代码生成方案

## 现有环境

- 后端：Spring Boot 3.5.16、Java 17、MyBatis-Plus 3.5.17、MySQL 8.0.36
- 代码根包：`com.agritrace.backend`，IDEA 2023.3.5
- Git：`main` 已成功推送到 GitHub（根据开发截图）
- 已有数据：`agri_traceability.planting_base` 中有一条“开发测试果园A”记录

## 设计原则

1. 不为 V1 增加区块链、传感器采集、App 或微服务。
2. 管理端角色先分 `ADMIN` 与 `FARMER`，消费者无需注册，按 `trace_code` 查询已发布批次。
3. 产地与产品是两个独立对象，通过 `trace_batch` 关联；二维码每个**批次**一个。
4. 产地风味是参考介绍，不等同检测结果；完整性评分只评估资料齐备程度，不等同质量或真实性。
5. 已发布批次修改流程、农户数据隔离和质检报告真实性不能依赖生成代码，必须实现业务验证。
6. SQL 文件只增建表和迁移旧表，不删除现有数据；依然建议先备份。

## 完整表结构，共 14 张

| 表名 | 功能 | 关系 |
|---|---|---|
| `sys_user` | 管理员和农户 | 1 用户可管理多基地/产品/批次 |
| `planting_base` | 种植基地 | owner_id → sys_user.id（旧测试数据可暂时为空） |
| `product_category` | 农产品分类 | 被产品引用 |
| `agri_product` | 农产品档案 | category_id → product_category；owner_id → sys_user |
| `trace_batch` | 溯源批次 | product_id、base_id、owner_id，trace_code 唯一 |
| `farm_record` | 农事记录 | batch_id → trace_batch |
| `harvest_record` | 采收记录 | batch_id → trace_batch，可多次采收 |
| `quality_inspection` | 质检记录 | batch_id → trace_batch |
| `circulation_record` | 流通事件 | batch_id → trace_batch |
| `trace_attachment` | 照片/PDF 元数据 | batch_id → trace_batch，文件本体不进数据库 |
| `origin_profile` | 基地＋产品特色档案 | base_id＋product_id 组合唯一 |
| `batch_audit` | 批次审核历史 | batch_id → trace_batch |
| `completeness_rule` | 完整性评价规则和权重 | rule_key 唯一 |
| `completeness_result` | 完整性评分快照 | batch_id → trace_batch |

SQL 中只建立最基础的外键和索引。字段业务枚举的合法转换、审核流程、关联对象所有权须由 Service 层验证。

## 一、执行完整建表 SQL

把 `农产品溯源系统_V1完整数据库设计.sql` 放在项目 `sql/03_schema_v1.sql`，用 MySQL 客户端执行：

```sql
SOURCE C:/Users/sujin/Desktop/ideaProjects/agri-traceability-system/sql/03_schema_v1.sql;
SHOW TABLES;
SELECT COUNT(*) AS table_count FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'agri_traceability' AND TABLE_TYPE = 'BASE TABLE';
SELECT id, base_name, owner_id FROM planting_base;
```

预计共有 **14 张基础表**，原来的果园测试数据仍然保留（owner_id 暂时为 NULL）。不要手动填写不存在的用户 ID。

建议执行前在 CMD 或 PowerShell 中运行：

```powershell
mysqldump -u root -p --databases agri_traceability --result-file=agri_traceability_backup.sql
```

备份文件建议放在 Git 忽略目录内或项目外，不要把真实用户信息提交到公开仓库。

## 二、安装新版代码生成器

采用官方 MyBatis-Plus `FastAutoGenerator` **3.5.17**，不采用图片中的旧版 3.4.1 生成器。将 `代码生成器_测试依赖片段.xml` 中的两个依赖添加到 `backend/pom.xml` 的 `<dependencies>` 内，再 Reload Maven。

将 `CodeGenerator.java` 复制到：

`backend/src/test/java/com/agritrace/backend/generator/CodeGenerator.java`

生成器使用 `src/test/java` 和 Maven `test` 依赖，避免将生成工具及模板引擎打入最终业务 JAR。

在 IDEA 里打开该文件的运行配置 `Run → Edit Configurations`：

- **Working directory** 指向 `C:\Users\sujin\Desktop\ideaProjects\agri-traceability-system\backend`
- **Environment variables** 配置 `MP_GEN_DB_PASSWORD` 为自己的 MySQL 密码；可选 `MP_GEN_DB_USER`、`MP_GEN_DB_URL`
- 密码不要写入 Java 代码，也不要提交 `.idea` 中包含密码的个人配置。

然后运行 `CodeGenerator.main`。

## 三、生成输出位置与合并方法

为了避免覆盖已经可以运行的 `PlantingBase` 类以及已有业务代码，本生成器不直接修改 `src/main/java`：

```text
backend/
  target/
    mp-generated/
      src/main/java/com/agritrace/backend/
        entity/
        dao/
        service/
        service/impl/
        controller/
      src/main/resources/mapper/
```

查看生成类，并**有选择地复制**到正式的 `backend/src/main/java/`。已经手写的 `PlantingBase`、`PlantingBaseMapper`、`PlantingBaseService`、`PlantingBaseServiceImpl`、`PlantingBaseController` 不要批量覆盖。可用 IDEA 的 Compare Files 对比，然后补齐实体字段（尤其是新增的 ownerId）。

> 生成的 `Controller` 不等于有真实的 CRUD REST 接口，更不等于已做好权限检查。必须补 Controller API、DTO/VO、输入校验、农户数据权限和统一异常处理。

## 四、建议的后续开发顺序

1. 一次性运行完整 SQL，检查 14 张表及关联。
2. 运行新版代码生成器，生成全部基础类；检查并合并文件。
3. 统一响应结构、全局异常处理、JWT 登录、数据权限；禁止普通农户查询其他用户的基地及批次。
4. 完成基地、分类、产品、批次、农事、采收、质检、流通 CRUD；列表使用分页。
5. 完成批次发布审核、完整性评分及缺失项提示。
6. 完成批次二维码查询、产地特色页面和附件展示；公众仅见允许公开的字段。
7. 创建 Vue 2 + Element UI 后台和移动端溯源页面，集中联调与测试。
8. 将 SQL、代码生成器与前后端源代码按功能进行真实的 Git 提交。

## 五、修改说明

后续变更数据库结构应新建 `sql/04_xxx.sql` 等迁移文件，**不要静默编辑已经在本机执行过的历史 SQL 脚本**，否则代码与数据库状态会不一致。

如果未来需要多农户协作、合作社组织、一个批次关联多个基地、批次拆分或多机构审核，应独立设计 V2，不能直接将现有外键与权限规则简化处理。
